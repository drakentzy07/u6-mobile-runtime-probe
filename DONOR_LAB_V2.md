# HIGHFLY — DONOR LAB 2.0

## Purpose
DONOR LAB 2.0 exists to validate and transplant real donor skills before HIGHFLY-specific redesign.

Official pipeline:

RAW DONOR -> dependency graph -> license gate -> FULL or SEMI-FULL transplant -> minimal HIGHFLY adapter -> retarget -> mobile QA -> KEEP / REJECT

## Definitions
- **FULL**: original executable skill block can be carried substantially intact, including its gameplay sequence and legally usable dependencies.
- **SEMI-FULL**: original mechanic/timing/structure is retained, but one or more presentation or engine dependencies must be replaced or translated.
- **CANDIDATE**: promising source found, not yet executed RAW.
- **REFERENCE ONLY**: architecture or mechanics may be studied; source assets are not donor assets.
- **BLOCKED**: source or license evidence is missing.
- **HighflyPorted** is never set true merely because a skill is documented or inspired by a donor.

## Non-negotiable rules
1. Never call an inspired HIGHFLY recreation a donor transplant.
2. Verify RAW donor behavior first whenever the original project can be run.
3. Preserve choreography, timing and mechanic before swapping presentation.
4. Replace only the dependency that is missing/incompatible/unlicensed.
5. Never commit raw Asset Store packages or ambiguous third-party assets to the public HIGHFLY repository.
6. REJECT means rollback the tested implementation; it does not erase the skill concept.
7. If a skill can be reproduced by tapping Basic Attack repeatedly, it is not ready.

6. Dragon Souls — projectile family

The roster expands only after each RAW path and dependency graph is auditable.
